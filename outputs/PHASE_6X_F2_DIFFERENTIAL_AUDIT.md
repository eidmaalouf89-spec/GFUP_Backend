   - **1458 are in chain-states where chain-onion says consultants are the current blocker** (`OPEN_WAITING_MIXED_CONSULTANTS`=1023, `OPEN_WAITING_SECONDARY_CONSULTANT`=430, `OPEN_WAITING_PRIMARY_CONSULTANT`=5). On these, chain-onion's lifecycle disagrees with DCC's `Att MOEX — Facile` per-indice tag. **Every single dropped FERMER row has an open consultant response** (2253/2253). So a consultant IS blocking on all of them.
   - **153 are `UNKNOWN_CHAIN_STATE`** — chain-onion can't classify them. Routing decision unclear without per-row inspection.
   - **1 is genuinely `OPEN_WAITING_MOEX` but has `moex_wait_days = 0`** — false drop caused by the `moex_wait_days > 0` clause.

2. **The chain-onion `current_state` and DCC `primary_tag` describe different things.** `current_state` is chain-lifecycle (one per family, encodes whose turn it is at the chain level); `primary_tag` reflects the latest indice's per-doc workflow (the latest indice may be in MOEX review even when the chain as a whole is waiting for a different actor). The two are NOT contradictory — they answer different questions.

3. **The real issue is downstream routing, not the F2 gate itself.** The 2253 + 747 dropped rows correctly fall out of MOEX buckets, but they then fail to match `CONSULTANT_A_ATTAQUER` (because their `primary_tag` is `Att MOEX — Facile`/`Arbitrage`, not `Att BET Primaire`/`Secondaire`) and end up in "no bucket". This is the 2977-row hole. Pre-F2, that hole didn't exist because FERMER_MAINTENANT was a catch-all for anything DCC tagged as MOEX-actionable, regardless of chain truth.

## Revised Gate Proposal

The current F2 gate (`current_state == "OPEN_WAITING_MOEX" AND moex_wait_days > 0`) is too coarse. Suggested replacement built from existing truth (no new helpers, no thresholds):

```
FERMER_MAINTENANT:
  primary_tag == "Att MOEX — Facile"
  AND (n_moex_open >= 1)                                # DCC: MOEX response is actually open
  AND (consultant_days_remaining is None or consultant_days_remaining > 0)
                                                         # no consultant currently late
  AND current_state NOT IN {"WAITING_CORRECTED_INDICE",
                            "CLOSED_VAO","CLOSED_VSO",
                            "DEAD_AT_SAS_A","ABANDONED_CHAIN",
                            "VOID_CHAIN","UNKNOWN_CHAIN_STATE"}
                                                         # explicitly exclude non-MOEX-actionable states

DECISION_MOEX:
  primary_tag == "Att MOEX — Arbitrage"
  + same three guards as above.

MOEX_SHAME_INTERNAL:
  Keep the current strict 6-signal predicate (16 rows retained matches plan estimate ~18-20).
```

**Why this is safer:**
- It uses DCC's `is_open` truth on the actual MOEX response (already exposed via `_get_latest_responses_for_doc` and 6X.E's columns) — that is the question "is MOEX actually called and waiting?".
- It uses 6X.E's `consultant_days_remaining` to exclude rows where a consultant deadline has passed (those belong in `CONSULTANT_A_ATTAQUER`, which catches them at Priority 6 anyway because of the `Att BET …` tag — but defensive guard here prevents the dual-blocker case from landing in MOEX).
- It uses an **exclusion list** of non-MOEX chain-states rather than requiring exactly `OPEN_WAITING_MOEX`. This admits rows in states like `CHAIN_OPEN_OBS` or other operational states where MOEX is genuinely the next step.
- It would require adding `n_moex_open` (or equivalent) to the DCC bulk output as a precursor (sister of 6X.E's columns). Small, additive, no new business logic.

## Recommendation

**Do NOT revert F2 wholesale.** The data shows F2's drops are mostly legitimate exclusions (closed chains, consultant-blocked chains). Reverting would put 612 closed-chain rows back into FERMER_MAINTENANT — which is the original bug the plan was trying to fix.

1. **Add an upstream closed-state filter to the actionable set** in `build_counter_attack_items`. Right now line 570 only excludes `focus_owner_tier == "CLOSED"`. Extend to also drop rows where `current_state in {"CLOSED_VAO", "CLOSED_VSO", "DEAD_AT_SAS_A", "ABANDONED_CHAIN", "VOID_CHAIN"}`. This removes 641 of the 2253 FERMER drops and any equivalent DECISION_MOEX closed rows from the audit population entirely. The plan's §6X.K validation #3 already requires this and only checks it post-rebuild — adding it as an explicit filter at line 570 makes the contract enforced rather than aspirational.

2. **Soften the F2 MOEX gates from `current_state == "OPEN_WAITING_MOEX"` to a chain-state EXCLUSION list** (states where MOEX is verifiably NOT the chain-level actor):
   ```

     primary_tag == "Att MOEX — Facile"
     AND moex_wait_days > 0

         "WAITING_CORRECTED_INDICE",                              # contractor blocker

Routing decision: either accept "no bucket" for these, or add a Priority 7-bis rule that reroutes to `CONSULTANT_A_ATTAQUER` when chain-onion says consultant blocker. **Recommend: accept "no bucket" for now** — these rows are in a real ambiguous state and need product-side judgement, not a gate.
