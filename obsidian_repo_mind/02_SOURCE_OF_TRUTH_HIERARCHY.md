# Source-of-Truth Hierarchy

> **From `README.md` §Source-Of-Truth Hierarchy and `docs/RUNTIME_SOURCE_OF_TRUTH.md`.**
> Read this before any debugging session.

---

## The hierarchy (rank 1 = highest authority)

| Rank | Layer | Location | Role | What it decides |
|---|---|---|---|---|
| 1 | **Raw GED dump** | `input/GED_export.xlsx` | Primary operational truth | Document identity, workflow rows, mission calling, lifecycle structure |
| 2 | **Flat GED** | `output/intermediate/FLAT_GED.xlsx` | Normalized operational layer | Active doc rows (GED_OPERATIONS), deduplicated, with consultant + status mapping applied |
| 3 | **report_memory.db** | `data/report_memory.db` | Persistent secondary consultant truth | Consultant answers that survive GED rebuilds (1,245+ active rows) |
| 4 | **effective_responses_df** | Runtime (composed in `src/effective_responses.py`) | Composed response truth | GED_OPERATIONS + eligible report_memory enrichment, LEFT-anchored on GED rows |
| 5 | **GF_V0_CLEAN.xlsx** | `output/GF_V0_CLEAN.xlsx` | Reconstructed GF output | **Not source of truth** — derived from layers 1–4 |
| 6 | **GF_TEAM_VERSION.xlsx** | `output/GF_TEAM_VERSION.xlsx` | Protected team export | Surgical patch of OGF using GF_V0_CLEAN; registered as run artifact |
| 7 | **UI** | `ui/jansa/*.jsx` | Presentation only | Renders what the backend sends; **makes no data decisions** |

---

## What each layer is allowed to decide

### Rank 1 — Raw GED

- Which documents exist (by `numero`)
- Which versions/indices exist
- Which workflow actors were called
- When submittals happened

> The pipeline reads this via `src/flat_ged/reader.py`. You never write back to it.

### Rank 2 — Flat GED

- Normalizes approver canonical names (via `consultant_mapping.py`)
- Normalizes statuses (via `status_mapping.py`)
- Excludes Exception List rows
- Splits into GED_OPERATIONS (active) and GED_RAW_FLAT (all rows)

> Auto-generated by `src/flat_ged_runner.py` every run. Never a user input. Never place `FLAT_GED.xlsx` in `input/`.

### Rank 3 — report_memory.db

- Persists HIGH/MEDIUM-confidence consultant answers from PDF reports
- Survives pipeline rebuilds — accumulated truth from multiple report imports
- Ingested via `stage_report_memory.py` (HIGH/MEDIUM gate only)

> Do not delete. Do not lower the confidence gate casually.

### Rank 4 — effective_responses_df

- Composed at runtime by `src/effective_responses.py`
- LEFT-anchored on GED rows — reports cannot inject brand-new workflow rows
- Five-value `effective_source` vocabulary: `GED`, `GED+REPORT_STATUS`, `GED+REPORT_COMMENT`, `GED_CONFLICT_REPORT`, `REPORT_ONLY` (prohibited)
- Used by both pipeline (`stage_report_memory`) and UI (`data_loader`)

> Changes here ripple to pipeline AND UI. Touch carefully.

### Rank 5–6 — GF outputs

- **Reconstruction targets** — derived, not authoritative
- GF_TEAM_VERSION is the deliverable (exported as `Tableau de suivi de visa DD_MM_YYYY.xlsx`)
- Registered in `run_memory.db` with sha256 for traceability

### Rank 7 — UI

- Pure presentation
- Receives shapes from `reporting.ui_adapter.adapt_*`
- If a UI number looks wrong, debug the backend layers 1–4, not the JSX

---

## The critical rule

> **GF is a reconstruction target. Never treat `GF_V0_CLEAN.xlsx` or `GF_TEAM_VERSION.xlsx` as authoritative for document identity or workflow state.**

If GF and GED disagree: GED wins. The discrepancy engine (`stage_discrepancy.py`) surfaces these as `DISCREPANCY_REPORT.xlsx`.

## Identity systems

Three identity systems coexist — they are NOT automatically bridged:

| Identity | Primary home | Notes |
|---|---|---|
| `(numero, indice)` | `flat_ged/*`, `chain_onion/*` | Stable across runs. Use for cross-run joins. |
| `doc_id` (UUID) | Pipeline runtime + `effective_responses_df` + `RunContext` | **Session-scoped — never persist** to chain output CSVs |
| `family_key = str(numero)` | Chain+Onion output CSVs | Stable across runs |

> When joining `flat_ged_ops_df` (numero/indice) with `effective_responses_df` (doc_id), the bridge is `query_library.py`. Be explicit — see `context/02_DATA_FLOW.md §Three identity systems`.

## Chain truth vs operational view (Phase 9, 2026-05-11)

The repository now distinguishes three layers when reading "the
documents":

1. **`output/chain_onion/CHAIN_REGISTER.csv`** — canonical chain layer.
   One row per chain (`family_key`). Source of truth for
   `latest_indice`, `current_state`, `portfolio_bucket`, `stale_days`.
2. **`ctx.latest_chain_df`** — in-memory canonical chain DataFrame.
   Built by `reporting.latest_chain_view.build_latest_chain_view`
   during context load. ~2,554 rows currently.
3. **`latest_enriched_view(ctx)`** — operational view. Intersection of
   `ctx.dernier_df` (pollution-prone but enriched with
   `_visa_global` / `_focus_owner_tier` / etc.) and
   `ctx.latest_chain_df.(numero, latest_indice)`. ~2,553 rows. THE
   canonical view for operational reporting (Action MOEX, dormants,
   DCC tags, fiches, drilldowns).

`ctx.dernier_df` itself is NOT a source of truth. In flat mode it
contains every `(numero, indice)` OPEN_DOC pair — 4,360 rows for 2,554
chains. It serves as: (a) the substrate for the
`_precompute_focus_columns` and `compute_focus_ownership` mutators,
(b) the substrate for history views and full-corpus search,
(c) the substrate that `latest_enriched_view` filters down.

**Decision tree for new code.**

- "I need to count chains / KPI / dormant / route / aggregate."
  → Use `latest_enriched_view(ctx)`.
- "I need chain identity only (family_key, latest_indice, etc.)."
  → Use `ctx.latest_chain_df`.
- "I need revision history / full-corpus search / all indices."
  → Use `ctx.dernier_df` directly.
- "I am a mutator (`_precompute_focus_columns`, `compute_focus_ownership`)."
  → Continue to mutate `ctx.dernier_df` in place by design.

See `README.md §Phase 9`, `context/11_TOOLING_HAZARDS.md §H-9`, and
`reports/STEP1_DERNIER_DF_INVENTORY.md` for the migration evidence.

## WorkflowEngine dual-attribute hazard

`WorkflowEngine.__init__` immediately filters `is_exception_approver == True`, stripping ALL SAS rows and Exception List approver rows from its internal copy. This means:

- `ctx.workflow_engine.responses_df` → **SMALLER**, no SAS rows (use for visa_global, deadline, non-SAS logic)
- `ctx.responses_df` → **FULL**, includes SAS rows (use for SAS-track analytics)

See [[11_DEBUGGING_SEAMS]] §H-3.
